Audited `feature/post-login-return` on 2026-08-17 (not yet merged at audit time): `app/Support/Auth/IntendedDestination.php` + `CustomerLandingUrl.php`, wired into `LoginController`/`RegisterController`. Verdict: safe, no CRITICAL/HIGH findings. 19/19 new tests (`PostLoginRedirectTest`) + related session-regen/tenant-isolation tests pass in Docker/SQLite.

**Why:** replaces a hardcoded post-login redirect with "return to where the customer came from", stored in session under the SAME key Laravel's own `guest()->intended()` uses (`url.intended`), deliberately never using `url()->previous()`/`Referer` (only `Session::previousUrl()`, which is always server-reconstructed from `$request->fullUrl()`, never client-supplied).

Key facts confirmed by reading vendor framework code (worth re-checking if this pattern shows up elsewhere):
- `Redirector::guest()` (`Redirector.php:71-84`) uses `$this->generator->full()` (safe) for GET, but falls back to `UrlGenerator::previous()` → **reads `Referer` header** for non-GET/`expectsJson()` requests — a real, pre-existing framework-level open-redirect surface. Not exploitable here today because every `auth`-protected mutating 'web' route has CSRF (`bootstrap/app.php` CSRF-except list is only `api/webhooks/*` + `webhooks/przelewy24`, neither `auth`-protected), so a forged cross-site non-GET request 419s before reaching `Authenticate`. Watch this: if a future CSRF-exempt route is added behind `auth`, this reopens.
- Safety of the whole mechanism rests entirely on `IntendedDestination::consume()` re-checking `isSameHost()` + `isSafePath()` (path denylist: `/admin`, `/platform`, `/livewire`, `/api`, `/webhooks`) at READ time, independent of how the value got into the session. This is verified by a dedicated test (`test_foreign_host_in_session_with_fresh_timestamp_is_rejected`) that seeds a foreign-host value with a fresh timestamp directly and asserts rejection.
- **Design fragility (MEDIUM, not currently exploitable):** `capture()`'s "auth-chain route" branch (previousRoute is `login`/`customer.register`/`password.*`) refreshes `url.intended_at` on an already-stored value WITHOUT re-validating it via `isSafeCandidate()`. This lets a `login ⇄ register ⇄ password.reset` loop keep a value "alive" past the stated 60-minute TTL. Harmless today only because `consume()` independently re-validates host+path every single time regardless of timestamp freshness or provenance — if `consume()`'s host/path recheck is ever "simplified away" as supposedly redundant, this refresh branch becomes a live open-redirect gadget with nothing else stopping it. Flag this invariant loudly if this file is touched again.
- Cross-tenant leak (VULN-003 class, [[project_retro_audit_2026-06-29]] adjacent): `CustomerLandingUrl::for()` correctly reads `$request->attributes->get('tenant')` (per-request, set by `ResolveTenant`), never `TenantFeature::currentTenant()`/`session('tenant_id')`. `IntendedDestination` cross-tenant safety comes from `isSameHost()` being checked independently at both capture time and consume time — a value captured on tenant-A's host is rejected at consume() if the login POST lands on tenant-B's host, regardless of shared/wildcard `SESSION_DOMAIN`.

**CORRECTION (team-lead caught this, 2026-08-17 — my original point 4 was WRONG):** I claimed "Filament panel doesn't use `IntendedDestination` at all — `AdminPanelProvider` overrides `LoginResponseContract` to always redirect to `/admin`." False. `AdminPanelProvider.php:16` imports `Filament\Http\Responses\Auth\Contracts\LoginResponse` — **the Filament v3 namespace, which does not exist in v4** (`interface_exists()` on it returns `false`, verified). The bind therefore targets a container key nothing ever resolves against — `App\Http\Responses\LoginResponse` is dead code. Filament's real default (`Filament\Auth\Http\Responses\LoginResponse::toResponse()`) runs instead: `return redirect()->intended(Filament::getUrl());` — reads the SAME `url.intended` session key `IntendedDestination` writes, via bare `Redirector::intended()` (`$session->pull('url.intended', $default)`), with **NO host/path revalidation at all** (unlike `IntendedDestination::consume()`). Concrete functional bug: a session that captured a customer-facing URL via `capture()` (e.g. browsed the shop, hit `/login`) and later logs into `/admin/login` without ever being intercepted on a protected admin page lands back on the shop page instead of `/admin`.
- **Security-relevant addendum I derived after the correction (communicated to team-lead, not yet independently re-confirmed by them):** because this consumption path has zero host/path validation, if `IntendedDestination::capture()`'s pre-validation (same-host, non-denylisted path) is ever bypassed — or if Laravel's own `Redirector::guest()` Referer-fallback (see vector 1 in this file) ever becomes reachable via a future CSRF-exempt route — the blast radius now includes **admin login**, not just customer login, since Filament's default response has no equivalent safety net to `IntendedDestination::consume()`.
- **Lesson for future audits:** when a bind/interface claim is "X overrides Y so Z never happens," verify the interface/class actually resolves (`interface_exists()`/`class_exists()` with autoload booted) before trusting the override — a bind to a nonexistent key throws nothing, it's silently inert, and the framework default runs unnoticed. Same class of failure as the [[claude-code-config.md]] "frontmatter newline kills the whole agent file" pattern: config that looks right and is silently dead.

**How to apply:** if a future PR touches `IntendedDestination.php`, re-verify that `consume()` still independently rechecks host+path (don't trust `capture()`'s validation alone) — that single check is the actual security boundary, everything else is convenience/UX. If a new CSRF-exempt route is ever added behind `auth` middleware, re-open vector 1 (Referer-based `url.intended` poisoning via `Redirector::guest()`) for review.

## Correction / addition (same-day follow-up, empirically verified)

My first pass on this audit said "no TrustProxies configured" and left it at that — I missed that **`bootstrap/app.php:73` configures `TrustHosts`** (a separate mechanism from `TrustProxies`, already on `develop`, not part of this feature): `$middleware->trustHosts(at: fn () => \App\Support\TrustedTenantHosts::patterns())`. Verified live (not just read) via `Illuminate\Http\Request::setTrustedHosts()` + `getHost()`:
- Active outside `local`/`testing` (`TrustHosts::shouldSpecifyTrustedHosts()`) — a forged `Host: evil.example` throws `SuspiciousOperationException: Untrusted Host` before any controller runs, on staging/prod.
- **Does NOT distinguish tenant subdomains from each other** — `tenant-a.registro.local` and `tenant-b.registro.local` are BOTH accepted (wildcard pattern `^(.+\.)?registro\.local$` = all subdomains of `app.url`). So `TrustHosts` closes off fully-external hosts but contributes nothing to cross-tenant isolation — `IntendedDestination::isSameHost()` is the ONLY defense against tenant-A-captured-value-consumed-on-tenant-B, on every environment including prod.
- Inert in `local`/`testing` — meaning the Docker test suite exercises `isSameHost()` alone, never `TrustHosts`, for this class of check.

**Verification method worth reusing:** proved cross-tenant rejection by booting the real app in the `app` container (`php -r 'require vendor/autoload.php; require bootstrap/app.php; ...'`) and calling `App\Support\Auth\IntendedDestination::capture()`/`consume()` directly against a shared `Illuminate\Session\Store` backed by `ArraySessionHandler` (pure in-memory, zero DB/file writes, safe under the read-only/no-dev-DB-write constraint) with two `Illuminate\Http\Request::create()` instances on different hosts. Always pair the "attack" run with a same-host control run to rule out a silently-broken harness (a call returning `NULL` proves nothing by itself if the harness can never return non-NULL). Same technique works for proving `Request::setTrustedHosts()`/`getHost()` behavior without needing a live nginx/staging environment.
